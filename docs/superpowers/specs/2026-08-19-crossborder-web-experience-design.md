# 跨境商品目录治理 Web 体验设计

## 1. 目标

Web 端服务的是商品目录治理人员，而不是 Agent 调试人员。用户进入项目后，第一眼应该知道：

- 当前项目处理什么市场、渠道和交付边界；
- 当前任务由哪些智能体处理、现在进行到哪一步；
- 哪些结果已经可以使用；
- 最终导出包在哪里、是否可以下载；
- 是否仍有审批、事实冲突或合规阻塞。

页面不承担 AgentTeams 编排职责，也不把 Matrix 消息、工具参数或内部事件当作产品内容展示。

## 2. 当前问题与根因

### 2.1 页面问题

当前页面存在四类可见问题：

1. 页面骨架仍接近旧通用协作工作区，项目领域信息被压缩在导航和卡片中。
2. 任务进展、工具调用、Artifact 和审批混在同一层，用户无法判断什么是过程、什么是交付。
3. 结果区把 JSON、Markdown、内部摘要和最终导出包按同一种文件平铺，导致“文件很多但没有结果”。
4. 最终导出包没有独立的交付状态和下载入口，用户必须在虚拟目录中自行猜测哪个文件最重要。

### 2.2 根因

根因不是单个 CSS 或组件，而是展示模型没有区分三种产品信息：

```text
执行过程：当前步骤、智能体进展、交接、等待和错误
业务结果：Product/SKU、合规发现、Listing 草稿、治理结论
交付物：最终导出包、报告、清单和下载状态
```

如果这三类信息共用一个文件列表或同一条消息流，任何视觉调整都会再次变成信息堆积。因此需要重建页面信息架构和结果分层，而不是在旧工作区上继续加面板。

## 3. 页面信息架构

### 3.1 项目总览

项目总览是进入项目后的默认页，内容顺序固定为：

1. 项目上下文：项目名称、目标市场、目标渠道、仅导出不自动发布。
2. 关键统计：项目素材、规范商品、任务数量、可交付产物。
3. 当前执行：运行中、待审批、失败或最近完成的任务。
4. 最近交付：优先显示最终导出包，其次显示报告和渠道草稿。

项目总览不展示工具调用，也不展示原始 JSON。

### 3.2 素材与目录

该页处理输入和业务事实：

- 项目素材上传、示例导入和选择；
- Product/SKU 规范事实与版本；
- 来源证据和事实冲突；
- ProjectResource 版本；
- 合规发现和 Listing 草稿摘要。

这里展示的是业务对象，不是 Agent 日志。JSON 只有在用户明确打开结构化详情时才允许作为辅助内容出现，并且默认不作为列表主项。

### 3.3 任务工作台

任务工作台采用三列结构：

```text
左列：动态任务阶段
中列：有效执行进展
右列：交付状态
```

左列：

- 只读取 `TaskDetail.task.steps`；
- 使用后端返回的步骤顺序、负责人、状态和结果摘要；
- 不补造固定阶段；
- 当前步骤、已完成步骤、等待审批和失败步骤有明确视觉状态。

中列：

- 将 `ProductEvent.action` 投影为中文的进展、交接、工具能力、产物、审批、错误和结果；
- 合并 AgentTeams 消息，但过滤 Matrix JSON、房间 ID、事件 ID、工具时间和重复摘要；
- 默认只展示对用户有决策价值的自然语言内容；
- 工具调用显示“读取商品事实”“执行美国服装合规检查”等能力名称，不展示原始入参和返回 JSON。

右列：

- 显示最终导出包数量和最近产物；
- 显示待审批和阻塞原因；
- 显示任务完成摘要或错误；
- 显示本次实际参与的智能体。

任务运行中没有完整计划时，显示“正在等待 Manager 形成计划”，而不是 `0/0` 空白流程图。

### 3.4 结果与文件

结果区不是普通文件浏览器，而是交付工作区。默认排序和视觉优先级：

```text
最终导出包
-> 治理审核报告
-> 合规报告
-> Shopify / eBay US 草稿
-> Product/SKU 目录
-> 过程性摘要
-> 原始或结构化内部文件
```

左侧可保留虚拟目录，但右侧默认必须显示交付摘要。最终导出包使用独立的交付面板，包含：

- 包名称；
- 已封存/可下载/被阻塞状态；
- 包内文件清单；
- 大小和完整性摘要；
- 下载按钮；
- “仅导出，不自动发布”边界说明。

JSON 文件处理规则：

- `manifest.json`、`retrieval-summary.json`、内部元数据默认归入“内部资料”，不进入最近交付；
- `*.json` 只有在没有可读报告或导出包时才作为次级结果显示；
- JSON 预览使用结构化摘要，不直接铺满原文；
- Artifact 原始文件仍可下载，平台不能删除或篡改证据。

如果没有最终导出包，结果区必须明确显示“尚未生成最终导出包”及原因，而不是让用户从空目录猜测。

### 3.4.1 最终导出包的生成边界

最终导出包不是前端把若干文件临时压缩出来的视觉效果，而是一次经过治理审核的正式交付产物。Manager 根据用户目标判断是否需要完整交付：

- 只做商品解析、合规检查或单个平台草稿时，可以只生成对应中间结果；
- 用户要求完整目录交付、Listing 包、导出或可直接交接的渠道资料时，Manager 应在必要的业务 Worker 完成后交给 `governance_reviewer_agent`；
- 治理审核通过并满足平台校验后，治理工具以 `create_export_package=true` 生成 `listing_package.zip`；
- 页面只读取这个 Artifact 的状态、成员数量、哈希和下载地址，不自行判断“文件齐了所以可以导出”；
- 若任务已完成但没有导出包，页面必须显示缺失原因或“本次目标未要求完整导出”，不能把中间 JSON 或 Markdown 冒充最终交付物。

已完成或失败的任务读取本地持久化投影，不在每次打开详情时重新请求 Matrix；只有排队、运行中和审批中的任务才持续与 AgentTeams 对账。这样既保留运行中的实时状态，也避免用户在查看历史结果时被无意义的同步延迟挡住。

这是一条由任务目标驱动的交付边界，不是固定的四阶段编排。AgentTeams Manager 仍然可以根据任务选择单个 Worker、并行 Worker 或完整协作路径。

## 4. 数据与状态边界

### 4.1 唯一真相源

前端只读取并投影以下后端数据：

- `Project`、`ProjectMaterial`；
- `TaskDetail`、`TaskStep`、`Approval`；
- `ProductEvent` 事件流；
- AgentTeams 消息接口；
- `Artifact`、`ProjectResource`；
- Product、Finding、Listing 数据接口。

前端不创建 Worker 状态、不推断任务步骤、不把消息列表当作任务数据库，也不维护第二套持久化 store。

### 4.2 结果分层

所有 Artifact 在投影层计算以下字段：

- `delivery_class`: `export_package`、`report`、`business_output`、`internal`；
- `directory`: `exports`、`governance`、`compliance`、`listings`、`catalog`、`reports`、`internal`；
- `is_primary_delivery`；
- `preview_mode`: `markdown`、`structured_summary`、`download_only`。

分类依据只能使用后端 Artifact 类型、文件名、负责人和元数据，不使用 LLM 猜测。最终导出包优先识别 `export_package`、`package`、`zip`、`listing_export` 等明确类型；不确定时归入内部资料并显示原因。

## 5. 组件边界

新的 Web 组件按产品领域组织：

```text
src/
  views/
    OverviewView
    CatalogView
    WorkbenchView
    ResultsView
  projection/
    taskProjection
    artifactProjection
  hooks/
    useProjectBundle
    useTaskLive
  components/
    delivery/PrimaryDeliveryPanel
    execution/TaskStageList
    execution/ActivityTimeline
    execution/ApprovalSummary
    results/ArtifactBrowser
    results/ArtifactPreview
```

旧 `ChatBox`、旧 `WorkFlow`、旧 `BottomBar`、旧状态适配器不作为新页面骨架，也不通过兼容层重新接入。

## 6. 视觉原则

- 使用安静、专业、偏目录治理的蓝灰和深青色，不使用营销式大卡片堆叠。
- 页面顶部保留明确项目上下文，避免用户不知道当前处理哪个项目。
- 最终交付包使用独立视觉层级，但不遮挡执行事实。
- 进展按时间和类别分组，交接和审批具有不同语义颜色。
- 所有按钮文案中文，内部字段名只在结构化详情中出现。
- 任务运行中、等待计划、等待审批、失败、完成和无结果都有专门空状态。
- 桌面 Web 使用三列工作台；窄屏时依次变为阶段、进展、交付三个区块。

### 6.1 低噪声界面原则

参考 AgentTeams 默认 Web 的优点：执行流、当前动作和工作列表应该连续可扫读，而不是把每条状态包装成一个彩色提示卡。跨境目录治理需要增加自己的 Product/SKU、合规、Listing、审批和导出语义，但不需要增加更多装饰层。

- 状态优先使用标题、左侧边线、图标、分隔线和文字，不使用大面积红/黄/蓝/绿背景；
- 一个区域只表达一个问题：当前动作、执行流、交付状态、审批阻塞不能互相嵌套成卡片；
- 过程内容采用时间线或连续列表，避免每条 Agent 消息都变成独立面板；
- 结果内容采用“交付物标题 → 文件事实 → 下载/下一步”的顺序，避免把过程 JSON 当成结果；
- 只有真正需要用户决策的阻塞、审批和错误才使用强调色，普通“运行中/已完成”不使用醒目色块；
- 保留 AgentTeams 的动态步骤和真实参与者，不把页面改造成固定业务向导。

### 6.2 现代产品视觉基线

页面需要达到可公开展示的现代 SaaS 产品标准，而不只是“能用的后台”：

- 使用系统无衬线字体、清晰的字号层级和稳定的 `0` 字符间距，避免旧式衬线标题和过度装饰；
- 背景使用浅灰白工作区，内容使用白色表面、细边框和轻阴影建立层级；
- 品牌色集中使用靛青作为主操作色，青绿色表示正向交付，黄色和红色只用于审批阻塞与真实错误；
- 圆角控制在 8—14px，卡片只用于项目统计、任务区、交付物和确实需要框定的重复内容；
- 不使用渐变背景、发光圆球、营销式大 Hero 或无意义的装饰图形；
- 关键 CTA、项目上下文、动态执行路径和最终导出包在首屏拥有明确视觉顺序；
- 结果和执行页面共享同一套颜色、间距、按钮和状态标记，不让不同页面看起来像不同产品。

## 7. 验证场景

实现后必须用真实后端数据验证：

1. 空项目：能看到项目边界和添加素材入口。
2. 有素材无任务：能选择素材并创建任务。
3. 任务刚创建：显示等待 Manager 形成动态计划，不出现 `0/0` 流程图。
4. 任务运行中：显示实际步骤、智能体、有效进展和交接，不显示 JSON 噪音。
5. 任务完成：右侧和结果区首要显示最终导出包，并可以独立预览/下载每个 Artifact。
6. 任务有审批：明确显示审批内容、阻塞状态和处理入口。
7. 只有内部 JSON：归入内部资料，并说明尚无可读交付物。
8. AgentTeams 暂不可用：页面显示服务状态和可恢复提示，不能伪造任务完成。

## 8. 实施顺序

1. 保留现有 API 类型和后端契约，重建 Artifact 投影和结果优先级。
2. 按本设计重建项目总览、任务工作台和结果区页面。
3. 删除旧 Web 页面骨架及其无用依赖，避免新旧展示并存。
4. 用 Cursor 生成的独立 HTML 样例作为视觉参考，不直接复制其静态数据或事件逻辑。
5. 完成 Web 类型检查、生产构建和真实 AgentTeams 场景验证。
